# 3. Validate the metrics pipeline

This is your first end-to-end test.

The expected flow is:

```text
Node Exporter ──┐
cAdvisor ───────┤
OTEL Collector ─┼──→ Prometheus ──→ Grafana
Prometheus ─────┘
```

Go to:

```text
http://localhost:9090/targets
```

You should see these scrape jobs:

```text
prometheus
node-exporter
cadvisor/docker
otel-collector
```

with `UP` status.

### Most important query

```promql
up
```

You should get one result per scrape target.

The interpretation is:

```text
1 → target is reachable
0 → target is unavailable
```

---

## CPU

```promql
100 - (avg(rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100)
```

This calculates approximately:

```text
100% - CPU idle percentage
```

→ CPU utilization.

---

## Memory

```promql
(1 - node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes) * 100
```

→ percentage of memory being used.

---

## Container CPU

```promql
rate(container_cpu_usage_seconds_total{name!=""}[5m]) * 100
```

The `{name!=""}` filter keeps the query focused on named containers.

---

## Top three memory-consuming containers

```promql
topk(3, container_memory_usage_bytes{name!=""})
```

This is a practical operational query:

> "Which containers are consuming the most memory right now?"

# 6. Validate the tracing pipeline

Now test the third pillar.

The path is:

```text
curl
  ↓
OTLP HTTP
  ↓
OTEL Collector :4318
  ↓
OTLP receiver
  ↓
batch processor
  ↓
debug exporter
  ↓
docker logs
```

The supplied trace simulates:

```text
GET /api/notes
       │
       └────→ SELECT notes FROM database
```

So there are two spans:

```text
Span 1
GET /api/notes
      │
      └── Span 2
          SELECT notes FROM database
```

The important relationship is:

```text
Trace ID
 ├── Span ID: 1111222233334444
 │     GET /api/notes
 │
 └── Span ID: 5555666677778888
       SELECT notes FROM database
       parent = 1111222233334444
```

That parent-child relationship is what allows a trace backend to reconstruct the request's journey.

Check:

```bash
docker logs otel-collector 2>&1 | grep -A 20 "GET /api/notes"
```

You should see both spans and their attributes.

# Row 1 — System Health

### CPU Usage

Gauge:

```promql
100 - (avg(rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100)
```

### Memory Usage

Gauge:

```promql
(1 - node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes) * 100
```

### Disk Usage

Gauge:

```promql
(1 - node_filesystem_avail_bytes{mountpoint="/"} / node_filesystem_size_bytes{mountpoint="/"}) * 100
```

### Targets Up

Stat:

```promql
sum(up)
```

You can compare that against:

```promql
count(up)
```

Together they answer:

> How many targets are healthy out of the total?

---

# Row 2 — Container Metrics

### Container CPU

```promql
rate(container_cpu_usage_seconds_total{name!=""}[5m]) * 100
```

Legend:

```text
{{name}}
```

This lets you see which container is consuming CPU.

### Container memory

```promql
container_memory_usage_bytes{name!=""} / 1024 / 1024
```

Again:

```text
{{name}}
```

as the legend.

### Container count

```promql
count(container_last_seen{name!=""})
```

This gives you a quick sanity check of the number of containers being observed.

# 11. Production readiness

The assignment asks you to identify what is missing before calling this production-ready.

The major additions are:

### Alertmanager

Current:

```text
Prometheus
   ↓
Alert
```

Production:

```text
Prometheus
   ↓
Alertmanager
   ↓
routing/grouping/silencing
   ↓
Slack / PagerDuty / email
```

### Trace storage

Currently:

```text
OTEL Collector
       ↓
debug exporter
       ↓
stdout
```

That's useful for learning but isn't a trace backend.

A production architecture could be:

```text
OTEL Collector
       ↓
Tempo / Jaeger
       ↓
Grafana
```

### Security

The learning environment uses local HTTP endpoints.

Production would require consideration of:

```text
TLS/HTTPS
Authentication
Authorization
Network restrictions
Secrets management
```

### Retention

You need explicit policies for:

```text
Prometheus metrics retention
Loki log retention
Trace retention
Storage limits
```

Otherwise storage can grow indefinitely.

### High availability

The exercise uses single instances.

Production may require:

```text
Prometheus replicas
Loki replicas
Grafana replicas
Durable object storage
Load balancing
```

# 12. Managed services comparison

The assignment asks you to compare this stack with Datadog, New Relic, or AWS CloudWatch.

The basic trade-off is:

```text
Build it yourself
        VS
Pay for managed observability
```

### Your stack

```text
Prometheus
Grafana
Loki
Promtail
OTEL
cAdvisor
Node Exporter
```

Advantages:

* control
* flexibility
* open-source ecosystem
* no vendor lock-in
* highly customizable

Costs:

* you operate everything
* upgrades are your responsibility
* storage is your responsibility
* HA is your responsibility
* alerting/routing needs configuration
* troubleshooting the monitoring platform becomes your job

### Managed platform

The provider handles much more of:

```text
Storage
Scaling
Availability
Upgrades
Integration
Alerting infrastructure
```

The trade-off is generally:

```text
less operational work
        +
faster setup
        -
ongoing service cost
        -
less control/vendor dependency
```

The correct choice depends on the organization's requirements rather than one solution universally being "better."

# 14. One important cleanup warning

The assignment finishes with:

```bash
docker compose down -v
```

The `-v` matters.

Without it:

```bash
docker compose down
```

stops/removes containers but preserves named volumes.

With:

```bash
docker compose down -v
```

you also remove:

```text
prometheus_data
grafana_data
loki_data
```

So only run it **after you've finished collecting screenshots and exporting anything you want to preserve**.

# 15. Final interview-level explanation

If an interviewer asks:

**"Walk me through the observability stack you built."**

You can answer:

> I built an eight-service observability stack using Docker Compose. Prometheus collects metrics from itself, Node Exporter, cAdvisor, and the OpenTelemetry Collector. Node Exporter provides host-level metrics, while cAdvisor provides container-level metrics. Grafana is used to visualize those metrics and manage alerting.
>
> For logs, Promtail collects Docker container logs and ships them to Loki, where I query them using LogQL and visualize them in Grafana. For traces, applications can send telemetry using OTLP to the OpenTelemetry Collector. The Collector receives and processes the telemetry and exports metrics to Prometheus while traces can be forwarded to a trace backend such as Tempo or Jaeger in a production environment.
>
> I also configured alert rules for conditions such as high CPU, high memory, disk usage, and unavailable targets. Finally, I created a unified Grafana dashboard combining infrastructure metrics, container metrics, and application logs so that an incident can be investigated from a single interface.

That's a much stronger answer than simply listing the tools.
