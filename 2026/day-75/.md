# 1. Loki vs Prometheus

A useful way to connect Day 73 and Day 75 is:

```text
Prometheus → metrics → PromQL
Loki       → logs    → LogQL
```

Loki follows a similar **label-based philosophy** to Prometheus.

The important difference from systems such as Elasticsearch is that Loki **doesn't index the complete log text**. It primarily indexes labels such as:

```text
job
container_name
filename
```

The actual log content remains available for querying.

### Why not index the full text?

The benefit is:

* simpler architecture
* lower storage/indexing overhead
* lower operational cost

The trade-off is:

* less powerful full-text search
* you need sensible labels to efficiently locate the relevant streams
* Loki isn't intended to replace a full-text search engine such as Elasticsearch

A particularly important warning from the assignment is **label cardinality**.

Good:

```text
container_name="notes-app"
job="docker"
```

Bad:

```text
user_id="123456"
request_id="abc123..."
```

Putting highly unique values into labels can create huge numbers of time series/streams and hurt performance.

Create:


Then:

```text

└── loki-config.yml
```

The supplied configuration establishes:

```yaml
auth_enabled: false

server:
  http_listen_port: 3100

common:
  ring:
    instance_addr: 127.0.0.1
    kvstore:
      store: inmemory
  replication_factor: 1
  path_prefix: /loki

schema_config:
  configs:
    - from: 2020-10-24
      store: tsdb
      object_store: filesystem
      schema: v13
      index:
        prefix: index_
        period: 24h

storage_config:
  filesystem:
    directory: /loki/chunks
```

For this learning environment:

```text
auth_enabled: false
```

means single-tenant mode without authentication.

```text
replication_factor: 1
```

means there is only one Loki instance, which is appropriate for this exercise rather than a highly available production deployment.

# 4. Promtail — the log collector

Loki doesn't normally go around reading every Docker log file itself.

That's Promtail's job.

The flow is:

```text
Docker
  │
  │ writes JSON logs
  ▼
/var/lib/docker/containers/
  │
  │ Promtail reads
  ▼
Promtail
  │
  │ HTTP push
  ▼
Loki
```

Create:

```bash
mkdir -p promtail
```

Then:

```text
promtail/
└── promtail-config.yml
```

The key configuration from the assignment is:

```yaml
server:
  http_listen_port: 9080
  grpc_listen_port: 0

positions:
  filename: /tmp/positions.yaml

clients:
  - url: http://loki:3100/loki/api/v1/push

scrape_configs:
  - job_name: docker
    static_configs:
      - targets:
          - localhost
        labels:
          job: docker
          __path__: /var/lib/docker/containers/*/*-json.log
    pipeline_stages:
      - docker: {}
```

There are three particularly important concepts here.

### `positions`

```yaml
positions:
  filename: /tmp/positions.yaml
```

Think of this as a **bookmark**.

Promtail needs to remember:

> "I've already read up to this point in this log file."

Without that state, it wouldn't know where to continue reading.

### `clients`

```yaml
clients:
  - url: http://loki:3100/loki/api/v1/push
```

This tells Promtail where to send the logs.

Notice:

```text
loki:3100
```

rather than:

```text
localhost:3100
```

because Promtail and Loki are separate Docker containers.

### `__path__`

```yaml
__path__: /var/lib/docker/containers/*/*-json.log
```

This tells Promtail which Docker log files to read.

---

# 5. Why the Promtail volumes matter

The Compose configuration mounts:

```yaml
- /var/lib/docker/containers:/var/lib/docker/containers:ro
```

This gives Promtail read access to Docker's container log files.

It's deliberately:

```text
:ro
```

meaning **read-only**.

It also mounts:

```yaml
- /var/run/docker.sock:/var/run/docker.sock
```

This allows Promtail to interact with Docker metadata and discover container information.

So conceptually:

```text
/var/lib/docker/containers
        ↓
actual log files

/var/run/docker.sock
        ↓
Docker/container metadata
```

# 8. LogQL

LogQL is Loki's query language.

The easiest way to understand it is to compare it with PromQL:

```text
Prometheus → PromQL → Metrics
Loki       → LogQL → Logs
```

### All Docker logs

```logql
{job="docker"}
```

### Prometheus container

```logql
{container_name="prometheus"}
```

### Search for errors

```logql
{job="docker"} |= "error"
```

`|=` means the log line contains the specified text.

The assignment notes that this is case-sensitive.

For case-insensitive matching:

```logql
{job="docker"} |~ "(?i)error"
```

---

# 9. Filtering logs

Exclude lines containing `health`:

```logql
{job="docker"} != "health"
```

Regex matching:

```logql
{job="docker"} |~ "status=[45]\\d{2}"
```

This looks for HTTP 4xx/5xx status patterns.

---

# 10. LogQL can produce metrics

This is an important concept.

You aren't limited to displaying raw logs.

You can calculate things from them.

### Count logs

```logql
count_over_time({job="docker"}[5m])
```

Meaning:

> How many log lines occurred during each five-minute window?

### Log rate

```logql
rate({job="docker"}[5m])
```

Meaning:

> At what rate are log lines being generated?

### Top containers by log volume

```logql
topk(
  5,
  sum by (container_name) (
    rate({job="docker"}[5m])
  )
)
```

Conceptually:

```text
Docker logs
    ↓
rate()
    ↓
group by container
    ↓
sum()
    ↓
top 5
```

This is where logs start behaving similarly to the metrics workflow you learned with PromQL.

# 11. Exercise queries

The assignment asks for all errors from `notes-app` during the previous hour.

A direct LogQL query is:

```logql
{container_name="notes-app"} |= "error"
```

Then restrict the Grafana Explore time range to **Last 1 hour**.

For error lines per minute:

```logql
count_over_time(
  {container_name="notes-app"} |= "error"[1m]
)
```

The important distinction is that the **time range can be controlled by Grafana Explore**, while `[1m]` in the query defines the range used for the calculation.

# 12. The most important part: Metrics + Logs

This is where Day 75 becomes much more valuable than simply "learning Loki."

Suppose you see:

```text
CPU usage
    ↑
    │
    │          /\
    │         /  \
    │________/    \____
              03:15
```

Prometheus tells you:

> Something unusual happened around 03:15.

You then inspect Loki for that same time:

```text
03:14:58 INFO request received
03:15:01 ERROR database connection timeout
03:15:02 ERROR retry failed
03:15:03 ERROR request returned 500
```

Now you have a much stronger understanding of the incident.

```text
Metric anomaly
      ↓
Identify timestamp
      ↓
Query logs for same period
      ↓
Find relevant error
      ↓
Investigate root cause
```

That's the essence of **observability correlation**.

# 14. Loki vs ELK

This comparison should definitely go into your Day 75 documentation.

|                     | Loki                                                       | ELK                                                    |
| ------------------- | ---------------------------------------------------------- | ------------------------------------------------------ |
| Main purpose        | Log aggregation                                            | Log aggregation/search                                 |
| Indexing            | Labels                                                     | Full-text/indexed fields                               |
| Query               | LogQL                                                      | Elasticsearch Query DSL/KQL                            |
| Complexity          | Relatively simple                                          | More components/operational overhead                   |
| Cost                | Generally lower for this model                             | Can become expensive at large scale                    |
| Search              | Less powerful full-text search                             | Powerful full-text search                              |
| Grafana integration | Excellent                                                  | Possible, but not Loki-native                          |
| Best fit            | Kubernetes/container observability, cost-conscious logging | Complex log search, analytics, full-text investigation |

### Interview answer

> I would choose Loki when I primarily need centralized container logs integrated with Grafana and Prometheus and want a simpler, label-based system. I would consider ELK when powerful full-text search, complex log analytics, and Elasticsearch's indexing capabilities are more important.

## The 7 Day-75 interview questions I'd practice

**1. What is Loki?**

> Loki is a log aggregation system from Grafana that stores and queries logs using a label-based approach rather than indexing the complete log content.

**2. What is Promtail?**

> Promtail is the log collection agent that reads logs, adds labels and metadata, and ships them to Loki.

**3. Why does Loki not index the entire log message?**

> To reduce indexing and storage overhead and keep the system simpler and cheaper. The trade-off is weaker full-text search compared with Elasticsearch.

**4. What does Promtail's `positions.yaml` do?**

> It records the position Promtail has reached in log files so it can continue reading from the correct location instead of repeatedly processing the same entries.

**5. Prometheus vs Loki?**

> Prometheus stores and queries metrics using PromQL; Loki stores and queries logs using LogQL.

**6. Why shouldn't you use user IDs as Loki labels?**

> User IDs can create extremely high label cardinality, producing a large number of distinct streams and increasing resource consumption.

**7. How do metrics and logs work together during an incident?**

> Metrics can identify the anomaly and its timing, while logs from the same time period can provide the detailed error or event that explains the anomaly.

### The key takeaway

Day 75 isn't really about memorizing Loki commands. The important operational pattern is:

> **Detect with metrics → locate the time window → investigate logs → identify the cause.**

That's the transition from simply **monitoring** a system to actually **debugging** it.
